# API reference

Base URL (local): `http://127.0.0.1:8000`. Interactive docs: `/docs` (Swagger UI) and `/redoc`. The machine-readable schema is `packages/api-client/openapi.json`, regenerated by `python scripts/export_openapi.py`.

All routes except `/health` live under `/api/v1`. If `API_KEY` is set on the server, send `X-API-Key: <key>`. Errors always look like:

```json
{"error": {"code": "not_found", "message": "No such job", "details": null}}
```

```bash
  -d '{"front":"What does LIFO stand for?","back":"Last in, first out."}'
```

## `POST /api/v1/ask`

Request:

```json
{
  "question": "How does a hash table handle collisions?",
  "k": 3,
  "mode": "technical",
  "model": null,
  "temperature": 0.2,
  "include_prompt": false,
  "no_cache": false
}
```

`mode` is the study style (technical, interview prep, quick summary). `model` must be one a request may name (see `GET /models`); any other is refused with a 422 and is never swapped for another. Response (abridged):

```json
{
  "answer": "A hash table has to deal with collisions ... [hashing.md]",
  "chunks": [
    {"doc": "hashing.md", "page": null, "end_page": null, "score": 0.62,
     "text": "Hash Tables > Collisions\nA collision occurs when ...", "url": null, "citation_url": null}
  ],
  "citations": [{"label": "hashing.md", "doc": "hashing.md", "page": null, "status": "ok"}],
  "unverified_citations": 0,
  "uncited": false,
  "model": "…",
  "cached": false,
  "prompt": null
}
```

## `POST /api/v1/ask/stream`

Same request body. The response is `text/event-stream`:

| Event | Data |
|---|---|
| `meta` | `{chunks, prompt?}` (sent first) |
| `token` | `{text}` (zero or more) |
| `done` | `{model, citations, unverified_citations, uncited, cached}` |
| `error` | `{code: llm_unavailable | llm_error | retrieval_error, message}` |

```bash
curl -N -X POST http://127.0.0.1:8000/api/v1/ask/stream \
  -H 'Content-Type: application/json' \
  -d '{"question":"What is the heap property?"}'
```

## `POST /api/v1/ask/agent/stream`

A slower, more careful path. Body: `{question, k (1-10), mode?, model?, temperature?}`. It always searches the server's index and is never cached. The workflow:

1. **rewrite** the question into a search query (it also searches the original wording, so a poor rewrite cannot hurt);
2. **retrieve**, then **grade**: the model says whether the passages are enough; if not, it searches once more with a query it suggests;
3. **answer** from the passages, streamed;
4. **verify** the citations; if the answer cited sources it was not given, it is **regenerated** once with the valid labels.

It uses at most 6 model calls per question (each counted against the daily cap). Planning failures (rewrite, grade) fall back to the plain behaviour; running out of quota stops the run with an `error` event.

| Event | Data |
|---|---|
| `step` | `{name: rewrite | retrieve | grade | answer | verify | regenerate, detail}` (one per stage, as it finishes) |
| `meta` | `{chunks}` (when answering starts) |
| `token` | `{text}` |
| `replace` | `{reason}`: discard the answer streamed so far; a corrected one follows |
| `done` | `{model, citations, unverified_citations, uncited, cached: false, llm_calls, regenerated}` |
| `error` | `{code: llm_unavailable | llm_error | retrieval_error | quota_exhausted | daily_limit, message}` |

Needs the optional `agent` extra (`pip install -e ".[agent]"`); without it the endpoint answers `503 agent_unavailable` and the rest of the API is unaffected.

## `POST /api/v1/agent/run/stream`

The model decides what to do. Body: `{task, max_steps (1-8, default 6), model?, temperature?}`. It is given the task and these tools: `search_documents`, `list_documents`, `read_page`, `solve_math`, `find_leetcode_problem` (and `save_flashcard` only when the deployment sets `AGENT_ALLOW_WRITES=1`; a request cannot enable it). Each turn it either answers or asks for tools; the server runs them and returns the results, until it answers or `max_steps` model turns are used, after which one forced wrap-up turn writes the answer.

| Event | Data |
|---|---|
| `thought` | `{text}` (the model's note alongside a tool call, when it writes one) |
| `tool_call` | `{name, arguments}` |
| `tool_result` | `{name, summary, error}` (a one-line summary, not the full result) |
| `meta` | `{chunks}` (the passages the tools returned) |
| `token` | `{text}` (the whole final answer; the last turn arrives complete) |
| `done` | `{model, citations, unverified_citations, uncited, steps, tool_calls, llm_calls, wrapped_up}` |
| `error` | `{code: tools_unsupported | llm_unavailable | llm_error | quota_exhausted | daily_limit, message}` |

Bounds: at most 4 tool calls per turn; an identical repeated call is refused; each tool result is cut at 6,000 characters; every model turn counts against the daily cap. A tool failure is returned to the model as `{"error": ...}` so it can recover. Needs the Gemini provider (other providers answer `tools_unsupported`) and the `agent` extra (`503 agent_unavailable` without it).


The stream always ends with `done` or `error`. It opens with an SSE comment line (`: stream open`) and sends `: keep-alive` comments whenever nothing else has gone out for `STREAM_KEEPALIVE_S` seconds (default 10), for example while a model call is pending; SSE readers ignore comments. A run still going `AGENT_DEADLINE_S` seconds (default 100) after the request arrived ends with `error` code `timeout`, so the stream finishes before the Lambda's 120 s limit can cut it off silently. A model failure mid-run (out of quota, overloaded after retries) ends with a typed `error` (`quota_exhausted`, `daily_limit`, `llm_error`); after the first turn the conversation stays on one model, so it does not fail over.

## Try first and practice

Attempt feedback makes one model call per request and Similar makes up to two. Neither caches nor stores anything, and the public-demo proxy allows both.

**`POST /api/v1/attempt/feedback`** splits `attempt` (up to 6,000 characters) into steps (up to 30), code lines (up to 200) or sentences (up to 30), and judges each against the `k` retrieved passages or the `context` you send. `judge` is `sources` (the default) or `problem`.

| Field in `items[]` | Meaning |
|---|---|
| `verdict` | `supported`, `contradicted` or `not_covered` by the passages |
| `citations` | checked the same way as `/ask` |
| `checked` | `true` when a `supported` or `contradicted` verdict has a verified citation. `false` means treat it as not checked against your sources |
| `basis` | `sources`, or `problem` (only with `judge: problem`): reasoned from the problem statement, not from your sources. A `problem` item is never `checked` and keeps no verified citation |
| `note` | a pointer, not the solution. A note or summary that restates the model's hidden answer is replaced, and `withheld` counts the replacements |

A unit without an item was not judged. An attempt that is too long or empty is refused with `422 attempt_too_long` or `422 attempt_empty`. `checked: true` means the cited passage was retrieved; it does not prove the verdict is right.

With `judge: problem` (the LeetCode page sends it when the problem has a statement) a unit may be judged on whether its reasoning works for the problem statement, including its constraints and edge cases. The server also sets `basis: problem` on a claimed source verdict unless a verified citation points to a passage holding at least half of the unit's content words, since citing the statement does not make it a source for a method it never mentions. In this mode every note and the summary are guarded more strictly: if the model gave no hidden answer key, or the text contains code the student did not write, or a note on a wrong unit (or the summary) states a correction, it is replaced with a neutral pointer. These verdicts are the model's reasoning and are not checked against anything.

**`POST /api/v1/practice/similar`** writes one new question from `context` (1 to 10 passages). `previous` (up to 5) lists questions already offered. The question is returned only if it cites a given passage, shares content with it, does not state its answer and is not a rewording of `question` or `previous`. Its answer is never returned. If the first draft fails one of these guards, or its reply is not valid JSON, the route makes one more model call, told only which guard failed (the rejected draft and its key are not sent back). A provider, quota or daily-limit failure is never retried here. Each call counts against the daily limit. If neither draft passes, the route answers `502 llm_error` with a message to try again.

Model failures on both routes use the standard error shape: `429 daily_limit`, `429 quota_exhausted`, `503 llm_unavailable` or `502 llm_error`.


## Limits

Flashcards, progress and history are stored in `data/study.db` (`STUDY_DB`); there are no accounts. Uploads: allowed types only, `%PDF-` signature checked, `MAX_UPLOAD_MB` (50) per file, bounded file count. Requests: `RATE_LIMIT_PER_MIN` (60) per IP, answered with `429` in the standard error shape.

Model calls: `DAILY_LLM_LIMIT` caps requests to the model per UTC day, counting retries and failover attempts (off by default). With `S3_BUCKET` the count is shared atomically across instances, and if it cannot be checked the call is refused. On Gemini's free tier a request can still fail when every model is busy or out of quota.

Citations: a check confirms that the cited document and page were among the retrieved passages. It does not confirm that the passage supports the claim.
